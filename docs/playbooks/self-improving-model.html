00Terrain map — what already exists

Stella already ships most of the machinery a self-improvement loop needs. The work is wiring, not greenfield. Know these surfaces before you touch anything.

stella-protocol

The Provider trait + CompletionRequest/Result. Every model — including your fine-tuned one — plugs in here.

stella-model

Concrete adapters: Z.ai (GLM 5.2), Anthropic, OpenAI, Gemini, Vertex, Bedrock. factory.rs, catalog.rs.

stella-core

The Engine step-driver. One model call per step, retry+backoff, loop detection, USD budget metering.

stella-pipeline

Orchestration: evaluate→enhance→route→execute→witness→verify→verdict→revise. The reward signal lives here.

stella-context

ContextStore: bi-temporal property graph, embedding index, episodic memory, recall/upsert.

stella-core :: hooks

HookRunner trait — lifecycle telemetry channel. Observes every step boundary. The instrumentation point.

stella-core :: calibration

CalibrationMap — existing precedent: the engine already learns (token-drift correction) from observed data. Model the improvement loop on this pattern.

bench/

Evaluation harness: SWE-bench (run_swebench.py), terminal-bench 2.1, smoke tests, loop-bench/.

Key realization

You are not building a self-improvement system from zero. Stella already has a closed feedback loop (verify→verdict→revise), a persistent memory (ContextStore), and an eval harness (bench/). Self-improvement = adding a training step on the cold path between "the loop produced an outcome" and "the loop runs again with a better model."

02Phase 1 — Collect execution traces

Before a model can improve, you need structured records of what it did and what happened. Stella already emits AgentEvents at every pipeline stage boundary and routes lifecycle telemetry through the hooks system. Capture them.

2.1

Tap the hooks channel

The HookRunner trait (stella-core/src/hooks.rs:249) is Stella's lifecycle telemetry bus. It fires at every step boundary with a structured JSON payload. Implement a hook that writes each event to an append-only trace store — a JSONL file or a SQLite table.

// stella-observatory or a new crate: stella-trace
pub struct TraceSink {
    out: Mutex<LineWriter>,
}

impl HookRunner for TraceSink {
    async fn run(&self, action: &HookAction,
                        payload_json: &str, _cwd: &str)
        -> Result<HookExecResult, HookExecError>
    {
        // payload carries: execution_id, step, model_ref,
        // tool calls, diff fingerprint, cost, timing
        self.out.lock().await.write_all(payload_json.as_bytes())?;
        self.out.lock().await.write_all(b"\n")?;
        Ok(HookExecResult::success())
    }
}
2.2

Capture the full trajectory, not just the final answer

A self-improving model learns from the process, so each trace record needs the complete staged trajectory. The pipeline already emits StageKind events — record the sequence for every run:

execution_idEngine turn receiptGroups steps into one task
model_refCompletionRequestWhich model produced this

prompt_messagesEngine accumulatorThe exact input (for SFT)
tool_calls[]Router eventsWhat the model chose to do

cost_usdBudgetGuardEconomic reward shaping
2.3

Write traces into ContextStore episodic memory

ContextStore already holds an episodic memory store with bi-temporal semantics. Rather than a flat file, upsert completed trajectories as episodic nodes so they are retrievable by similarity for future few-shot prompting and exportable as training data.

Integration point

ContextStore::upsert (stella-context) — write the trajectory. ContextStore::recall — already used by the pipeline to inject relevant past experience. Your traces become both training data and live retrieval fodder.

  • Hook emits on every step boundary with full payload
  • Trace store captures: prompt, tool calls, diff, cost, stage trajectory
  • Traces upserted to ContextStore episodic memory
  • Smoke test: run stella run on a sample task, confirm a complete trace lands

03Phase 2 — Extract reward signal

This is Stella's superpower for self-improvement: the pipeline already verifies every outcome through a deterministic-first ladder and an independent model judge. That verdict is your reward. You don't need to build a reward model from scratch — you need to export the one Stella already computes.

3.1

Read the verification ladder's verdict

The verify stage (stella-pipeline/src/verify.rs) produces a LadderDecision — a tiered, evidence-based verdict that runs before any model judge call:

Ladder outcomeReward labelConfidence
SubmitFast (deterministic flip + green tests)+1.0 rewardProven
DeterministicFail (red touched tests)−1.0 penaltyProven
ModelJudge PASS (escalated, inconclusive evidence)+0.5Judged
ModelJudge FAIL−0.5Judged
Heuristic fallback0.0 (discard)Unverifiable

Why this matters

Stella's ladder is deterministic-first — it only spends a model judge call on genuinely inconclusive evidence (design lesson L-E11). That means most of your reward labels are grounded in real test execution, not another model's opinion. This is rare and valuable training signal.

3.2

Enrich the reward with cost and efficiency

A purely outcome-based reward ignores that the model took 12 steps and $0.40 to do what should take 3 steps and $0.05. Stella already meters both:

  • Step count — from EngineConfig::max_steps tracking; fewer is better.
  • USD cost — BudgetGuard meters every completion into per-role envelopes (triage/worker/judge).
  • Revision count — how many times the verify→revise loop fired before passing. Zero = ideal.
# Composite reward per trajectory
reward = outcome_label            # +1 / -1 / +0.5 / -0.5
       − (0.02 × step_count)      # penalize thrashing
       − (0.5  × cost_usd)        # penalize spend
       − (0.1  × revision_count)  # penalize not getting it right first
3.3

Respect the feedback airlock when labeling

Critical subtlety: Stella's feedback airlock (witness::airlock) redacts model-authored text (judge reasoning, distress guidance) before it reaches the worker, to prevent the worker from gaming sealed test material. When you export reward labels, use the deterministic outcome as ground truth — treat judge reasoning as soft signal only, never as a training target. Otherwise you risk training the model to fool the judge.

Guardrail

Never train on the content of distress-guidance prompts or judge reasoning as if they were correct outputs. They are steering text, not ground truth. The deterministic flip oracle and test execution are your only hard labels.

  • Each trace tagged with LadderDecision outcome + reward scalar
  • Cost, steps, revisions factored into composite reward
  • Judge reasoning marked soft-signal-only, never a training target
  • Heuristic-fallback traces discarded (no reliable label)

04Phase 3 — Build the training dataset

Turn labeled traces into datasets matched to the training algorithm you'll use. Three datasets serve three improvement strategies.

4.1

SFT set — from the proven winners

Filter for trajectories with reward ≥ +0.8 (deterministic SubmitFast, low cost, zero revisions). These are exemplars — the model doing exactly the right thing. Format as supervised fine-tuning pairs: (prompt_messages, ideal_completion).

{
  "prompt": <the Engine's message array at step N>,
  "completion": <the tool-call / answer the model produced>,
  "outcome": "submit_fast",
  "task_class": "single_task",
  "repo": "stella",
  "reward": 0.94
}
4.2

Preference pairs — for DPO

For the same prompt where you have a chosen (high-reward) and rejected (low-reward) trajectory, build Direct Preference Optimization pairs. Stella's best-of-N candidate isolation (stella-pipeline/src/candidate.rs) already generates multiple candidates per task and scores them — mine it for natural preference pairs.

{
  "prompt": ...,
  "chosen":  <completion from CandidateScore::DeterministicPass>,
  "rejected": <completion from CandidateScore::Failed>
}
4.3

RL rollout set — for online improvement

For RL (GRPO/PPO), you don't pre-label — you need a set of tasks the model can attempt, with a verifier that returns reward. Stella is that verifier. Define the rollout set as repeatable bench tasks (see Phase 4) and let the verify ladder score each rollout live.

4.4

Deduplicate and decontaminate

ContextStore fingerprints embeddings — use it to deduplicate near-identical traces. Critically, hold out the bench tasks from the training set so evaluation stays honest (no train/test leakage).

Contamination risk

If SWE-bench or terminal-bench instances leak into SFT data, your eval numbers will lie. Partition strictly: training traces from real usage, evaluation from the frozen bench harness.

05Phase 3 — Fine-tune the model

The training itself happens outside Stella (on a GPU cluster with your framework of choice — Axolotl, TRL, OpenRLHF). Stella's job ends at producing clean data and a reliable verifier. Start simple, escalate only when returns plateau.

5.1

Stage A — Supervised fine-tuning (SFT) on winners

Always start here. SFT on the proven-winner dataset (4.1). This teaches the model Stella's style — the staged reasoning, tool-call format, when to stop. It's the cheapest, most reliable first improvement and it de-risks everything after.

Base model: a small open model in stella-model's catalog (e.g. a GLM-class or Llama-class model you can host). Keep parameter count modest — the goal is agentic behavior, not world knowledge.

5.2

Stage B — Preference optimization (DPO) on pairs

Once SFT plateaus, run DPO on the preference pairs (4.2). This sharpens decision-making — the model learns which of two plausible actions actually verifies. DPO is cheaper than full RL and often captures most of the gain.

5.3

Stage C — Online RL with Stella as the verifier (advanced)

The endgame: the model attempts bench tasks, Stella's verify ladder scores each attempt in real time, and the reward backpropagates. This closes the loop fully — the model literally learns from Stella's own verification. Wire the reward function (3.2) as the RL reward and the FlipOracle / test execution as the environment.

Architecture

RL training loop → calls Stella Engine::run_turn on a bench task → pipeline produces LadderDecision + cost → reward scalar → gradient step. The Provider trait is the interface the training server speaks to dispatch completions to the in-training model.

06Phase 4 — Re-evaluate on the bench harness

Never trust training loss. Prove the new model is better on Stella's frozen evaluation suite before it touches production. The bench/ directory is your battleground.

6.1

Run the existing harnesses

  • SWE-bench — bench/run_swebench.py. Real GitHub issues → real PRs. The gold standard for coding agents.
  • terminal-bench 2.1 — bench/terminal-bench-2.1-protocol.md. Terminal-native agentic tasks.
  • smoke tests — bench/smoke/. Fast regression gate.
  • loop-bench — bench/loop-bench/. Specifically tests the agent's loop behavior — critical for a self-improving model.
6.2

Compare against the baseline, not just absolute numbers

Run the same harness with the baseline (pre-fine-tune) model and the candidate model, same seeds, same bench instances. Report:

MetricSourceGoal
Resolve rateflip oracle pass↑ vs baseline
Avg steps per taskEngine step count↓ (more efficient)
Avg USD per taskBudgetGuard↓
Revision rateverify→revise count↓ (right first time)
Judge escalation rateLadderDecision::ModelJudge↓ (more deterministic passes)
6.3

Gate the deploy on a regression check

A model that gains 3% on SWE-bench but regresses 15% on loop-bench is a net loss. Define a promotion gate: candidate must beat baseline on the primary metric and not regress beyond a threshold on any secondary. This mirrors Stella's own philosophy — proportionate verification, escalate on evidence.

Watch for reward hacking

If resolve rate rises but step count and cost spike, the model may be brute-forcing. If judge-escalation drops but resolve rate is flat, it may be gaming the flip oracle. Always read metrics together, never in isolation.

  • Candidate model run on full bench suite, same seeds as baseline
  • Side-by-side comparison on all five metrics
  • Promotion gate defined and documented
  • No regression beyond threshold on any secondary metric

07Phase 4 — Redeploy through the Provider trait

Stella's clean port architecture makes deployment trivial in principle. The Provider trait (stella-protocol/src/provider.rs:69) is the single integration surface — your fine-tuned model is just another adapter.

7.1

Serve the fine-tuned model behind an OpenAI-compatible endpoint

The path of least resistance: host your fine-tuned model with vLLM, TGI, or llama.cpp server — all expose an OpenAI-compatible chat completions API. Stella's existing openai.rs adapter then points at your endpoint with zero new code.

# stella settings: point the openai adapter at your served model
[model.stella-self]
provider = "openai"
base_url = "http://gpu-node:8000/v1"
model_id = "stella-sft-v1"
api_key = "local"
7.2

Or — write a native adapter (if you need streaming/mid-call features)

If you need complete_observed (mid-stream tool-call speculation), implement the full Provider trait directly. Look at stella-model/src/zai/ or stella-model/src/anthropic/ as templates — they already handle SSE streaming, retry classification, and error typing.

impl Provider for SelfImprovingAdapter {
    fn id(&self) -> &str { "stella-self" }

    async fn complete(&self, req: CompletionRequest)
        -> Result<CompletionResult, ProviderError>
    {
        // dispatch to your served model, classify errors
        // exactly like zai.rs / anthropic.rs do
    }
}
7.3

Register it in the catalog and resolver

Add the model to stella-model/src/catalog.rs and ensure ProviderResolver::provider_for (stella-pipeline/src/ports.rs:34) routes ModelRefs for your model to your adapter. The pipeline's role system (triage/worker/judge) lets you deploy selectively — e.g. use the fine-tuned model as the worker while keeping a frontier model as the judge, preserving the independence guarantee (judge ≠ worker, L-E11).

Preserve judge independence

Stella requires the judge to be a different model than the worker. If you fine-tune for the worker role, keep the judge on a frontier model. The pipeline degrades the authored-witness path when judge == worker — don't lose that safety net.

08Phase 5 — Automate the cycle

Once one manual cycle works, wire it into a scheduled pipeline so improvement compounds. This is where "self-improving" becomes literal.

8.1

Schedule the nightly cycle

A cron / CI job that runs the full loop: collect the day's traces from production usage → reward them → merge into the dataset → train an incremental checkpoint → evaluate on bench → auto-deploy if the promotion gate passes. Each cycle is a git-tagged model version with its bench report archived.

8.2

Let ContextStore seed each new run with prior wins

Because traces live in episodic memory, ContextStore::recall already injects relevant past experience into new runs. As the model improves, its better trajectories overwrite worse ones in memory — the retrieval itself gets better over time, compounding the fine-tuning gains.

8.3

Model the automation on the CalibrationMap precedent

The engine already has a self-correcting subsystem: CalibrationMap learns token-drift correction from observed (estimated, actual) pairs and feeds the correction back into compaction decisions — seeded from persisted telemetry at session start. This is structurally identical to what you're building at the model level. Follow that pattern: observe → persist → reload → apply, all behind a feature flag, off by default.

8.4

Version everything

Every model version, every dataset snapshot, every bench report, every trace batch — versioned and archived. If a cycle produces a regression that slips past the gate, you need to roll back to the previous model version instantly. The ModelRef system already versions models by id — extend that discipline to the whole cycle.

09Guardrails — what can go wrong

Self-improvement is a power tool. These are the ways it cuts you, and how Stella's existing design helps you avoid each.

RiskMechanismMitigation (Stella-native)
Reward hacking Model learns to game the flip oracle or write tests that trivially pass The witness-protocol's tamper exclusion + independent witness authoring. The model can't see the sealed test. Keep judge ≠ worker.
Train/test contamination Bench instances leak into SFT data → fake eval gains Strict partition: production traces for training, frozen bench for eval. Dedupe via ContextStore fingerprints.
Distribution shift Fine-tuned model drifts from the prompt format the pipeline expects SFT data is from the real Engine message format by construction (trace capture). Format can't drift if you train on actual traces.
Catastrophic regression A bad cycle degrades the model in production Promotion gate (6.3) + instant rollback via versioned ModelRef. Never auto-deploy without passing bench.
Feedback loop pathology Model trains on its own outputs → mode collapse / amplification Always mix in human-verified traces and frontier-model demonstrations. Periodically reset to a fresh base + SFT rather than endlessly chaining.
Cost runaway RL rollouts or best-of-N eval burns GPU/API budget Stella's BudgetGuard meters every call. Wrap the training cycle in a USD ceiling, same as a production turn.

The unbreakable rule

The deterministic verification ladder is the ground truth. The model judge is advisory. Human review is the final backstop on any auto-deployed model. Never let the self-improvement loop bypass all three — a model that can't pass real tests, confirmed by an independent judge, signed off by a human, has no business in production, no matter what the training loss says.
