# Where Stella puts things on your disk

Every path Stella reads or writes, what lives there, and whether it is safe to
commit, delete, or share.

Three tiers, in the order the config chain merges them:

| Tier          | Location                                                            | Committed?              |
| ------------- | ------------------------------------------------------------------- | ----------------------- |
| **user**      | `~/.stella/` (override: `$STELLA_HOME`)                             | no — your machine only  |
| **managed**   | OS-wide, administrator-owned (override: `$STELLA_MANAGED_SETTINGS`) | no — deployed by an org |
| **workspace** | `<repo>/.stella/` + `<repo>/stella.toml`                            | **partly — see below**  |

> **Status:** `stella.toml` **works today** (see `docs/design/config-system/`).
> `settings.json` is still read when no `stella.toml` exists, so nothing breaks
> if you have not migrated. Run `stella migrate config` to convert; it keeps
> the JSON until you delete it yourself. Where both exist, the TOML wins and
> stella says so.
>
> One exception: `[mcp.servers]` in `stella.toml` is not consumed yet — MCP
> servers still load from `.stella/mcp.toml`. Stella warns rather than failing
> to start them silently.

## Workspace — `<repo>/`

The only tier that is ever committed. The split is deliberate: everything a
teammate should get is outside `private/`, everything machine-local is inside
it, and `.stella/.gitignore` enforces the line.

```sh
<repo>/
├── stella.toml ................. PROJECT CONFIG — live. COMMIT THIS.
│                                 Reviewed in PRs like any source file. Never
│                                 holds a secret: an inline `api_key` here is a
│                                 load ERROR, naming api_key_env instead.
├── .env ........................ committed, non-secret defaults
├── .env.local .................. NEVER COMMIT — per-developer secrets
├── .env.<mode>.local ........... NEVER COMMIT — e.g. .env.production.local
│                                 (.env.example / .sample / .dist are never read)
│
└── .stella/
    ├── .gitignore .............. generated; ignores private/ and machine-local state
    ├── settings.json ........... PROJECT CONFIG — legacy. Read only when no
    │                             stella.toml exists. `stella migrate config`
    ├── mcp.toml ................ MCP servers this repo connects to
    │                             stdio servers spawn processes → trust-gated
    ├── domains.toml ............ GENERATED by `stella init` — the domain taxonomy
    │                             tagging memories, reflections, and graph nodes.
    │                             Safe to commit; regenerate rather than hand-edit.
    ├── workspace.json .......... durable workspace UUID (survives a `mv` of the
    │                             checkout, which is why replication keys off it)
    │
    │   ── Content the agent reads. All markdown-with-frontmatter. Commit these. ──
    ├── rules/
    │   └── <name>.md ........... enforceable guardrails
    ├── skills/
    │   └── <slug>/SKILL.md ..... know-how selected into context automatically
    ├── commands/
    │   ├── <slug>.md ........... /slug — a reusable prompt template
    │   ├── <slug>.toml ......... same thing, TOML spelling (not a feature tier)
    │   └── <ns>/<slug>.md ...... a namespace → /<ns>:<slug>
    ├── agents/
    │   └── <slug>.md ........... named persona definitions, listed by /agents
    ├── tools/
    │   └── <name>.toml ......... custom script tools — one per file, next to the
    │                             script it runs. argv is spawned directly, never
    │                             through a shell. Gated by the managed authority
    │                             bit `project_custom_tools`.
    ├── memories/ ............... durable notes the agent wrote
    │
    │   ── Working output. Usually gitignored; delete freely. ──
    ├── artifacts/ .............. generated media (images, video) from tool calls
    ├── attachments/ ............ files pasted into the TUI
    ├── screenshots/ ............ captured page/CI screenshots
    ├── explorations/ ........... saved exploration bundles
    ├── proposals/ .............. pending context-record proposals awaiting review
    ├── exports/ ................ `stella export` output
    ├── context/packs/ .......... assembled context packs
    ├── worktrees/ .............. git worktrees for isolated fleet tasks
    │
    │   ── Machine-local state. NEVER commit; safe to delete (you lose history). ──
    ├── private/
    │   ├── store.db ............ THE session store — transcripts, events, turns.
    │   │                         Event-sourced; the fold everything else reads.
    │   │                         `stella doctor [--repair]` checks/quarantines it.
    │   ├── codegraph.db ........ the code graph built by `stella init`
    │   ├── context.db .......... embeddings + recall index for adaptive context
    │   ├── fleet.db ............ fleet attempts, commits, and dollars
    │   ├── reflections.jsonl ... per-execution reflections (mined into skills)
    │   └── mcp_oauth.json ...... OAuth tokens for MCP servers — SECRET
    │
    └── stella.duckdb ........... LEGACY, pre-migration telemetry. Read-only
                                  fallback; a newer store.db supersedes it.
```

### What is safe to commit

**Commit:** `stella.toml` / `settings.json`, `mcp.toml`, `domains.toml`,
`workspace.json`, and everything under `rules/`, `skills/`, `commands/`,
`agents/`, `tools/`.

**Never commit:** `private/` (session content and OAuth tokens), `.env.local`,
`.env.*.local`.

**Your call:** `memories/` — commit to share learned context with the team,
gitignore to keep it personal.

> **The root `stella.toml` changes the stakes.** A file next to `README.md` gets
> committed far more readily than one three directories deep. That is why an
> inline `api_key` is a load-time **error** at project scope: use `api_key_env`,
> or `~/.stella/credentials.toml`.

## User — `~/.stella/`

Your machine, all projects. Never committed anywhere.

```
~/.stella/                      (override the whole tree with $STELLA_HOME)
│
│   ── Config ──
├── stella.toml ................. USER CONFIG — live. Merges under project.
├── settings.json ............... USER CONFIG — legacy, read only if no TOML
├── mcp.toml .................... MCP servers available in every project
│
│   ── Secrets. All owner-only (0600). ──
├── credentials.toml ............ provider API keys, plaintext.
│                                 Created 0600 from birth; zeroized in memory on
│                                 drop; warns (never refuses) if the mode is loose.
│                                 Write with `stella auth set <provider>`.
├── integrations.json ........... GitHub / Linear OAuth tokens (`stella connect`)
├── web_auth.toml ............... stored web credentials
├── cloud.json .................. cloud account registration + org_id
│
│   ── Cross-project state ──
├── usage.db .................... the telemetry hub — every project on this
│                                 machine, aggregated. Backs `stella usage` and
│                                 the observatory's user tier.
├── catalog.db .................. the MODEL CATALOG: model cards, pricing
│                                 versions, and aliases learned from telemetry.
│                                 Refreshed only on explicit request — Stella
│                                 does not phone home on its own.
├── installation-id ............. random per-install UUID (owner-only)
├── sessions/ ................... the session registry — what `stella resume` lists
├── notifications/ .............. queued /inbox notifications
│
│   ── Same content kinds as the workspace, available everywhere ──
├── rules/                        On a name collision the WORKSPACE copy wins.
├── skills/
├── commands/
├── agents/
└── tools/
```

### Migrated from an older location

Everything user-global used to live in the OS data dir. Stella moves entries
across on first run and leaves the old directory in place; existing files are
never overwritten.

| Platform | Old location                                        |
| -------- | --------------------------------------------------- |
| macOS    | `~/Library/Application Support/stella/`             |
| Windows  | `%APPDATA%\stella\`                                 |
| Linux    | `$XDG_DATA_HOME/stella/` → `~/.local/share/stella/` |

Override with `$STELLA_DATA_DIR` (wins over `$STELLA_HOME` for the data tier).

## Managed — organization policy

Administrator-owned. Read-only to Stella; the file's _location_ is what grants
it authority.

```
macOS   /Library/Application Support/stella/settings.json   (→ stella.toml)
other   /etc/stella/settings.json                           (→ stella.toml)
        $STELLA_MANAGED_SETTINGS  — override (also how tests point at a fixture)
```

Only this tier's `[authority]` block is honored. It is a **ceiling**, not a
default: a tool it denies cannot be re-enabled by the user or the project, and
it is computed from the managed file alone so no later merge can raise it.

---

## Directories Stella reads but does not own

On `stella init`, definitions authored for other coding agents are
**symlinked** into `.stella/` rather than copied, so edits stay in one place.
Never clobbers an existing name; never links a symlink.

```
<repo>/.claude/{commands,skills,agents}/   ─┐
<repo>/.agents/{commands,skills,agents}/   ─┴─► symlinked into <repo>/.stella/
```

## How the three tiers combine

Ordinary settings merge **per field**, so a managed base URL and a user API-key
variable compose into one effective provider rather than replacing each other.

```
      user  ──►  managed  ──►  project          project wins ordinary fields
        └───────────┴──────────────┘
                    │
        ┌───────────┴───────────────────────────────────┐
        │  …but the org still wins two ways:            │
        │                                               │
        │  1. TRUST ROLLBACK — an untrusted project      │
        │     loses hooks, context providers, and every  │
        │     credential-routing field (base_url,        │
        │     api_key, api_key_env, mcp.registry_url).   │
        │     Open it with STELLA_TRUST_PROJECT=1.       │
        │                                               │
        │  2. THE CEILING — [authority] is read from the │
        │     managed file alone. Nothing downstream,    │
        │     including a trusted project, can raise it. │
        └───────────────────────────────────────────────┘
```

Hooks are the exception to per-field merging: they **concatenate**. Any tier may
add a gate; none may remove another's.

## Environment overrides

| Variable                  | Effect                                                                                                                                                                                                                  |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `STELLA_HOME`             | relocates the whole user tree (default `~/.stella`)                                                                                                                                                                     |
| `STELLA_DATA_DIR`         | relocates the data tier (`usage.db`, `installation-id`)                                                                                                                                                                 |
| `STELLA_MANAGED_SETTINGS` | points at the managed policy file                                                                                                                                                                                       |
| `STELLA_TRUST_PROJECT=1`  | trusts this repo's hooks, context providers, and credential routing                                                                                                                                                     |
| `STELLA_PROJECT_HOOKS=1`  | legacy, hooks only                                                                                                                                                                                                      |
| `STELLA_NO_SETTINGS=1`    | **benchmark isolation** — skips all three config tiers _and_ rules, memories, skills, custom tools, MCP config, and persisted session state. A task image's preinstalled state is outside the frozen system under test. |

## Deleting things safely

| Want to                     | Delete                                                             | You lose                                                  |
| --------------------------- | ------------------------------------------------------------------ | --------------------------------------------------------- |
| reset one project's history | `<repo>/.stella/private/`                                          | transcripts, graph, embeddings, fleet ledger              |
| rebuild the code graph      | `<repo>/.stella/private/codegraph.db`                              | nothing — `stella init` rebuilds it                       |
| clear generated output      | `artifacts/ attachments/ screenshots/ exports/`                    | generated files only                                      |
| sign out of everything      | `~/.stella/credentials.toml`, `integrations.json`, `web_auth.toml` | all stored credentials                                    |
| full reset, all projects    | `~/.stella/`                                                       | every key, all cross-project telemetry, the model catalog |

`private/store.db` is the one worth a thought before deleting: it is the
event-sourced fold every other surface reads. `stella doctor --repair` moves a
corrupt store aside (renamed, never deleted, WAL/SHM siblings travelling with
it) and salvages what is readable, rather than making you delete it yourself.
