# Diagnostic codes

A record's `code` is stable, versioned public surface (`doc:diagnostics` §11):
operators alert on it, docs link it, and it outlives the message text. This
file is that surface's reference — one section per code the tree emits.

**The facts blocks and section list are generated** from the emit sites by
`make diag-reference` (`scripts/diagnostic-codes.py`); the prose under each
facts block is hand-written and preserved across regeneration. The gate
(`make diagnostic-codes`) fails when this file and the tree disagree — an
undocumented code, a section for a code nothing emits, two crates claiming one
code, stale facts, or prose still reading as the placeholder. Fields listed
are the statically visible ones; a section says so when an emit site builds
fields the scanner cannot name.

Codes are grouped by the crate that owns their facet vocabulary (§5.1 of the
spec: the crate that owns the vocabulary owns the rendering).

### `agent.candidate.delivery`

<!-- facts:begin — generated by `make diag-reference`; do not edit by hand -->
- **Level:** `info`
- **Emitted from:** `crates/stella-cli/src/diag_bridge.rs`
- **Fields:** `seq`, `outcome`, `created`, `modified`, `deleted`, `lines_added`, `lines_removed`, `proven`, `reason`
<!-- facts:end -->

What an isolated run did with the winning candidate's workspace — the one record that answers "did this run's work reach my tree?" without inferring it from whether `agent.file.change` records happened to follow.

`outcome` is `delivered` or `declined`, and which one it is decides the rest of the fields. A `delivered` record carries the per-kind file counts and line deltas adoption itself measured, plus `proven`: `false` means no passing verdict stood behind the work, and it is *not* a failure — a verdict is a claim about the work, not what decides whether the work exists, so a run that came to rest on the revise rung or ran out of clock still delivers. A `declined` record carries `reason` instead:

| `reason` | What happened | What to do |
|---|---|---|
| `nothing_created` | No candidate workspace was ever created (a degradable setup failure), so no model call was made and there are no bytes anywhere. | Look for the earlier snapshot/isolation error; this record is a consequence, not the cause. |
| `integrity_refusal` | The pipeline refused the candidate on an integrity finding — it wrote through its isolation, its witness artifact was mutated after its baseline was pinned, or its worktree moved after verification. | Treat as a real refusal. The bytes are not the bytes any stage examined, so delivering them would ship something nothing looked at. |
| `adopt_failed` | Delivery was sanctioned and `git apply` refused it, usually because the same files were edited mid-run. Adoption is all-or-nothing, so **nothing** was applied. | The candidate workspace is preserved; the accompanying error names the conflicting paths and where the work is recoverable from. |

The candidate workspace path is deliberately **absent** from this record: it is a filesystem path, which §7 forbids as a field value, and a per-run temporary directory tells a reader nothing `outcome` does not. The path appears in the event stream (`candidate_delivery`) and in the operator-facing message on the rail.

Correlate with `agent.verifier.verdict` to separate the two questions that look alike: the verdict says whether the run *proved* itself, this record says whether the work *survived*. An empty `delivered` record — all counts zero — is a real answer and is distinct from every `declined` one.

### `agent.run_complete`

<!-- facts:begin — generated by `make diag-reference`; do not edit by hand -->
- **Level:** `info`
- **Emitted from:** `crates/stella-cli/src/diag_bridge.rs`
- **Fields:** `seq`, `model`, `cost_usd`
<!-- facts:end -->

The **run** finished, and this is its receipt: the model that answered last
and the total cost across every turn the run contained. Exactly one of these
per run, and nothing follows it — it is the only record that means "nothing

`diag.panic`), failed (look for a non-retryable `agent.error`), or is still
going. Do not read `agent.turn_complete` as this record: a run that wraps
several turns emits one of those per turn, and stopping at the first reports
a fraction of the cost.

### `agent.tool.call`

<!-- facts:begin — generated by `make diag-reference`; do not edit by hand -->
- **Level:** `debug`
- **Emitted from:** `crates/stella-cli/src/diag_bridge.rs`
- **Fields:** `seq`, `tool`, `args_bytes`
<!-- facts:end -->

The model asked for a tool: which built-in (`tool`, a closed vocabulary — an MCP or invented name classifies as `other`) and how large the arguments were (`args_bytes`). The arguments themselves are model output and never reach this plane. The `seq` correlates with the matching `agent.tool.result`, which since #3149 also carries the same `tool` field, so the join is a convenience rather than a requirement.

The collapse to `other` is a declared gap, not a silence (#3149): a tool name outside the closed set is model-chosen text, which the diagnostic plane's no-`String` rule keeps out by construction. Per-tool attribution for MCP, script, and foundry tools lives in `store.db`'s `tool_calls` table, which records the raw name for every call — join there when an `other` needs a name.

### `agent.tool.result`

<!-- facts:begin — generated by `make diag-reference`; do not edit by hand -->
- **Level:** `debug` or `warn`
- **Emitted from:** `crates/stella-cli/src/diag_bridge.rs`
- **Fields:** `seq`, `tool`, `ok`, `duration_ms`, `speculated`, `output_bytes`
<!-- facts:end -->

A tool finished: which tool (`tool`, the same closed vocabulary as `agent.tool.call` — #3149), `ok`, `duration_ms`, `output_bytes`, and whether the result was produced speculatively (`speculated`). Emitted at `warn` when the tool failed, `debug` otherwise — so a default stderr filter shows failures and only failures, and the failing line names its tool on its own: the matching call record was emitted at `debug` and is invisible at that filter, so attribution cannot depend on a join. A result whose call the bridge never observed (a stream joined mid-turn) classifies as `other`, and an `other` is attributed via `store.db`'s `tool_calls` table, which records the raw name. Slow runs are usually a few large `duration_ms` values here.
