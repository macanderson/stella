title: How stella built a tool to check the weather

A person asked stella for the weather in Los Angeles. stella has no
web search tool. It has no network of its own. The first answer was
"I can't check that." Then they asked: *can you build a tool that can?*

Yes. It showed how little you need. Here is what happened.

## Two files

The workspace gained two files.

```text
.stella/tools/
├── weather.toml            # the manifest. the whole contract
└── scripts/
    └── weather.py          # the script that runs
```

One command checks that the tool is wired up.

```bash
stella tools --validate
#   ✓ .stella/tools/weather.toml (weather_lookup)
#   1 manifest(s) checked: 1 ok, 0 with errors, 0 warning(s)
```

On the next session, `weather_lookup` sits with the built-in tools.
The agent calls it like any other tool. There is no SDK. There is no
Rust code. There is no build step. There is no API key.

## Read the docs

stella started from the
[Custom Tools](/docs/agent-tools/custom-tools) page. It also read the
sample manifests under `plugins/` in the repo.

That page settled the design.

- A full plugin was more than this job needed. A plugin has four parts:
  context, tools, hooks, and panels. A
  [custom tool](/docs/agent-tools/custom-tools) is a TOML file plus a
  script, dropped into `.stella/tools/`.
- The manifest sets a `name`, a `description`, and a `command`. The
  command is a list of args. It is started with no shell. The
  `[input_schema]` is JSON Schema, written as TOML.
- The script gets input in two ways. The whole JSON object arrives on
  stdin. Each top-level value also arrives as a
  `STELLA_INPUT_<UPPER_SNAKE_KEY>` env var. A simple script needs no
  JSON parser.
- Exit code 0 means stdout is the tool result. Any other exit code
  means stderr is the error the model sees.

## The manifest

```toml title=".stella/tools/weather.toml"
name = "weather_lookup"
description = "Look up the current weather for any location worldwide. Uses the free Open-Meteo API (no API key needed). Returns condition, temperature, feels-like, humidity, and wind."
command = ["python3", ".stella/tools/scripts/weather.py"]
timeout_ms = 30000

[input_schema]
type = "object"
required = ["location"]

[input_schema.properties.location]
type = "string"
description = "The city or place to get weather for, e.g. \"Los Angeles\" or \"Tokyo, Japan\"."

[input_schema.properties.units]
type = "string"
enum = ["fahrenheit", "celsius"]
description = "Temperature units. Defaults to fahrenheit."
```

The docs named rules that mattered here.

1. **`name` must match `^[a-z][a-z0-9_]{1,63}$`.** Names that clash
   with built-in tools, or with retired tools like `web_fetch`, are
   refused. `weather_lookup` is clear of that set.
2. **`command` is a list of args, not one string.** A bare string
   fails to parse. The tool then never loads.
3. **Inputs go under `[input_schema]`, not `[parameters]`.** An
   unknown table is ignored. The tool would then have an empty schema.
   It would have no way to take the city name.

The `description` field is the only text the model sees when it
chooses a tool. It says what the tool returns. It also says that no
API key is needed.

## The script

`weather.py` uses only the Python standard library. It uses `urllib`
and `json`. There is nothing to install. It calls the free
[Open-Meteo](https://open-meteo.com) APIs.

1. **Turn the place name into a point on the map.** The call goes to
   `geocoding-api.open-meteo.com`. It returns latitude and longitude.
2. **Fetch the current conditions.** The call goes to
   `api.open-meteo.com/v1/forecast`. It uses the units you asked for.
3. **Print a short summary.** That is the sky (from the WMO weather
   code), the temperature, what it feels like, the humidity, and the
   wind.

Input handling follows the docs.

```python title=".stella/tools/scripts/weather.py"
raw = sys.stdin.read()
data = json.loads(raw) if raw.strip() else {}

location = (data.get("location")
            or os.environ.get("STELLA_INPUT_LOCATION") or "").strip()
if not location:
    print("weather error: missing required input: location", file=sys.stderr)
    sys.exit(1)
```

Stdin comes first. `STELLA_INPUT_*` is the fallback. On a bad input
the script exits non-zero. It prints the reason on stderr. That text
is what the model sees as the tool error.

## Check it first

stella lets a bad manifest through at discovery time. The bad file
is only a note. The session keeps running. So the check had two passes.

**The strict check.**

```bash
stella tools --validate
```

One manifest was checked. One was ok. There were zero warnings. This
check catches a `command[0]` that cannot run. It catches a
`timeout_ms` that is out of range. It catches a reserved name. It
does this before a real run spends budget to find the same bugs.

**Live runs.** The input was piped the same way the engine pipes it.

```bash
$ echo '{"location": "Los Angeles"}' | python3 .stella/tools/scripts/weather.py
Current weather for Los Angeles, California, United States (as of 2026-09-21T00:30 local):
  Condition:   Clear sky
  Temperature: 66.8°F (feels like 69.7°F)
  Humidity:    86%
  Wind:        3.5 mph
```

Tokyo in celsius worked. London through the `STELLA_INPUT_LOCATION`
env var worked. The missing-input error path worked. Each one matched
the docs.

## Why it was easy

The build took a few minutes. The reasons sit in the design.

- **The manifest is the whole contract.** There was nothing to learn
  about how stella works inside. The docs say a tool is a TOML file
  and a script. That was true.
- **No SDK, no build, no extra libraries.** The script is the Python
  standard library. It talks to an API that needs no key. `command`
  is started directly, so the script is what runs.
- **Input can arrive two ways.** JSON on stdin, or `STELLA_INPUT_*`
  env vars. You can test the script by hand with `echo | python3`.
  No test harness is needed.
- **A failure is one line.** Exit non-zero. Print to stderr. The
  error text goes back to the model.
- **`stella tools --validate` closes the loop.** Run it before the
  tool is called in a real session.

<Callout type="info">
One limit: workspace manifests sit behind the
[project trust boundary](/docs/configuration/settings#the-project-trust-boundary).
So `.stella/tools/` loads only in a trusted repo
(`STELLA_TRUST_PROJECT=1`). For a tool you want in every repo, put
the manifest in `~/.stella/tools/`. That directory always loads.
</Callout>
