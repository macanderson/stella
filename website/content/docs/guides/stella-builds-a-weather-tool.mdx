title: How stella built a weather tool
description: A user asked stella for the weather. stella had no web tool. It wrote one.

Someone asked stella for the weather in Los Angeles. stella has no web
search. It has no network of its own. The first answer was "I can't check
that." Then they asked if it could build a tool.

It could. Two files. A few minutes. No extra packages.

## Two files

```text
.stella/tools/
├── weather.toml            # the manifest — the whole contract
└── scripts/
    └── weather.py          # the script that runs
```

One command checks that the tool is wired up:

```bash
stella tools --validate
#   ✓ .stella/tools/weather.toml (weather_lookup)
#   1 manifest(s) checked: 1 ok, 0 with errors, 0 warning(s)
```

On the next run, `weather_lookup` sits with the built-in tools. The agent
calls it like any other tool. No SDK. No Rust. No build step. No API key.

## The docs

It did not guess how plugins work. It read the
[Custom Tools](/docs/agent-tools/custom-tools) page. It also read the
sample files under `plugins/`.

That page set the shape:

- A full plugin was more than this job needed. A custom tool is a TOML
  file plus a script. You drop both in `.stella/tools/`.
- The file sets a `name`, a `description`, and a `command`. The command
  is a list of args. There is no shell. It also sets an `input_schema`.
- The script gets the whole input as JSON on stdin. Each plain field is
  also an env var. A small script needs no JSON parser.
- Exit code 0 means stdout is the result. Any other code means stderr is
  the error the model sees.

## The manifest

```toml title=".stella/tools/weather.toml"
name = "weather_lookup"
description = "Look up the current weather for any location worldwide. Uses the free Open-Meteo API (no API key needed). Returns condition, temperature, feels-like, humidity, and wind."
command = ["python3", ".stella/tools/scripts/weather.py"]
timeout_ms = 30000

[input_schema]
type = "object"
required = ["location"]

[input_schema.properties.location]
type = "string"
description = "The city or place to get weather for, e.g. \"Los Angeles\" or \"Tokyo, Japan\"."

[input_schema.properties.units]
type = "string"
enum = ["fahrenheit", "celsius"]
description = "Temperature units. Defaults to fahrenheit."
```

Three rules from the docs mattered:

1. `name` must match `^[a-z][a-z0-9_]{1,63}$`. A name that clashes with a
   built-in tool, or a retired one like `web_fetch`, is refused.
   `weather_lookup` is clear of that list.
2. `command` is a list of args, not one string. A bare string does not
   parse. The tool does not load.
3. Inputs go under `input_schema`, not `parameters`. An unknown table is
   skipped. The tool would then have no inputs, and no way to get the city.

The `description` is the only text the model sees when it picks a tool.
Say what the tool returns. Say that no API key is needed.

## The script

`weather.py` uses only the Python standard library. That is `urllib` and
`json`. Nothing to install. It calls the free
[Open-Meteo](https://open-meteo.com) APIs.

1. Turn the place name into a latitude and a longitude. That call is
   `geocoding-api.open-meteo.com`.
2. Fetch the current weather, in the units the caller asked for. That
   call is `api.open-meteo.com/v1/forecast`.
3. Print a short summary. The sky text comes from the WMO code. The line
   also has the temp, what it feels like, the humidity, and the wind.

The input path follows the docs:

```python title=".stella/tools/scripts/weather.py"
raw = sys.stdin.read()
data = json.loads(raw) if raw.strip() else {}

location = (data.get("location")
            or os.environ.get("STELLA_INPUT_LOCATION") or "").strip()
if not location:
    print("weather error: missing required input: location", file=sys.stderr)
    sys.exit(1)
```

Stdin comes first. The env var is the backup. A bad call exits with a
non-zero code and the reason on stderr. That text is the tool error the
model sees.

## Prove it

The docs say stella is loose when it finds tools. A bad file is only a
note. The run keeps going. So the check had two passes.

The strict check:

```bash
stella tools --validate
```

One file checked. One ok. No warnings. This check catches a
`command` that cannot run, a `timeout_ms` that is out of range, or a
reserved name. It does that before a real run spends money to find them.

Then a live run. The input is piped the same way the engine pipes it:

```bash
$ echo '{"location": "Los Angeles"}' | python3 .stella/tools/scripts/weather.py
Current weather for Los Angeles, California, United States (as of 2026-09-21T00:30 local):
  Condition:   Clear sky
  Temperature: 66.8°F (feels like 69.7°F)
  Humidity:    86%
  Wind:        3.5 mph
```

Tokyo in celsius worked. London through the env var worked. The
missing-input error worked. Each one matched the docs.

## Why it was easy

The build took a few minutes. The shape of the tool is why.

- The file is the whole contract. There was nothing to learn about the
  inside of stella. The docs say a tool is a TOML file and a script.
  The build was that.
- No SDK, no build, and no packages. The script is Python's own library
  talking to an API that needs no key. `command` starts as a list, so
  the script is what runs.
- Input can be JSON on stdin, or env vars. You can test the script by
  hand with `echo | python3`. No harness.
- A failure is one line. Exit with a non-zero code. Print to stderr.
  The text goes back to the model.
- `stella tools --validate` checks the file before a real run calls it.

<Callout type="info">
Workspace files load only in a trusted repo. Set `STELLA_TRUST_PROJECT=1`.
The rule is the
[project trust boundary](/docs/configuration/settings#the-project-trust-boundary).
For a tool you want in every repo, put the file in `~/.stella/tools/`.
That folder loads on its own.
</Callout>
