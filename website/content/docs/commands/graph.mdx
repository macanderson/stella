title: stella graph
description: Query the code graph built by stella init — definitions, references, callees, callers, imports, importers, and neighbors.
---

Ask the code graph structural questions about your workspace: where a symbol is defined, who references it, what a definition calls, which call sites name it, what a file imports, who imports it, or a file's immediate neighborhood. It is fully offline — it reads `.stella/private/codegraph.db` and needs no API key.

## Synopsis

```bash
stella graph <op> <target>
```

## What it does

`stella graph` reads the code-graph index that [`stella init`](/docs/commands/init) builds at `<workspace>/.stella/private/codegraph.db`. Because it only reads that local index, it makes no model calls and needs no provider credential — it is instant and works on a plane.

`<op>` is one of seven operations, and `<target>` is interpreted according to the operation:

<CardGrid size="md">
  <OptionCard name="definitions <symbol>">
    Where is this symbol defined? `<target>` is a symbol name.
  </OptionCard>
  <OptionCard name="references <symbol>">
    Where is this symbol used? `<target>` is a symbol name.
  </OptionCard>
  <OptionCard name="callees <symbol>">
    What does this definition call? Recorded call sites inside the definition's
    span. `<target>` is a symbol name.
  </OptionCard>
  <OptionCard name="callers <symbol>">
    Which call sites name this symbol? Best-effort — matched by name, so
    same-name methods conflate, and the answer says so. `<target>` is a symbol
    name.
  </OptionCard>
  <OptionCard name="imports <path>">
    What does this file import? `<target>` is a workspace-relative file path.
  </OptionCard>
  <OptionCard name="importers <path>">
    Which files import this file? `<target>` is a workspace-relative file path.
  </OptionCard>
  <OptionCard name="neighbors <path>">
    What is this file's immediate graph neighborhood? `<target>` is a workspace-relative
    file path.
  </OptionCard>
</CardGrid>

<Callout type="info">
You do not have to run [`stella init`](/docs/commands/init) first. `stella graph` **builds the index on first use** if it isn't there, and every query runs a catch-up pass over files that changed since the last one — so answers track your working tree without a manual re-index. Running `init` up front just means the first query doesn't pay for the full build, and it also produces the domain taxonomy, which querying alone does not.
</Callout>

If the catch-up pass fails, the query still answers — from whatever the index already held — and says so rather than hiding it:

```text
warning: the code graph index pass failed — answering from what the index already holds, which may be stale
```

That is the one case where a re-`init` is the fix.

## Examples

Find where a symbol is defined and who uses it:

```bash
stella graph definitions resolve_provider_config
stella graph references resolve_provider_config
```

Walk the call structure around a function — what it calls, and who calls it
(callers is name-matched, so treat it as a shortlist, not proof):

```bash
stella graph callees run_turn
stella graph callers run_turn
```

Inspect a file's imports, its importers, and its neighborhood:

```bash
stella graph imports    crates/stella-cli/src/config.rs
stella graph importers  crates/stella-cli/src/config.rs
stella graph neighbors  crates/stella-cli/src/config.rs
```

Check the blast radius of a file before you change it — who would you break:

```bash
stella graph importers src/db/schema.ts
```

Confirm a symbol you are about to rename is defined exactly once:

```bash
stella graph definitions parse_age_window
```
