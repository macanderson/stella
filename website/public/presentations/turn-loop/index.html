Part 1 · 01

The one-sentence version

Stella asks a model what to do next, does it, shows the model what happened, and asks again — until the model stops asking for things.

That is genuinely the whole engine. Everything else in this deck is one of two things: bookkeeping around that loop (money, memory, safety, size) or extra structure wrapped around the loop (planning first, proving afterward).

The core loopthis runs once per step
TURN

One turn

One prompt from a person, worked all the way to an answer. A turn holds many steps.

STEP

One step

Exactly one model call, plus the tools that call asked for. Twelve phases run around it.

SESSION

One session

One run of the program. Many turns. The conversation carries across them.

Part 1 · 03

Two loops, six doors

This is the answer to "how many versions of the loop do we have?" The honest answer is two, and one of them is built on top of the other.

There is one step loop at the bottom. Above it there is one optional wrapper — the staged pipeline — that adds planning before and proof after. Six commands lead in. Four go through the wrapper, two go straight to the loop.

Interactive · doors into the engine click a door to trace its path

Six doors, one engine

Every door ends in the same place. The differences are: does a plan get made first, does a proof get demanded after, who is watching, and where the work is written down.

website/content/docs/agent-engine-paths.mdx

The one subtlety. The two direct doors are not the same depth. stella --plain calls run_turn and lets it loop. stella-serve calls run_step itself, one step at a time — which is exactly what lets a host save its place and pick up later. Same phases, different driver.

Part 1 · 04

What every route shares

Before the differences, the promises. These hold no matter which door you came in by — a fleet worker and a one-line question run the exact same code here.

01

One step loop

One model call per step. Tools run. Results feed back. Repeat. There is no hidden swarm of agents and no coordinator process quietly running somewhere else.

02

One tool stack

The same layered set of tools: the built-ins, wrapped by MCP server tools, wrapped by custom script tools. Routes only add things on top — never swap the base out.

03

Memory rides along

Relevant memories and skills are pulled in per prompt and added after the stable part of the prompt, so the provider's cache still works.

04

Money is metered everywhere

Every route counts dollars. --spend-limit makes that a hard ceiling; without it, spend is still tracked for the summary.

05

Everything is written down

Each turn opens a record: files touched, tools used, memories cited, cost, outcome. That record is what stella stats and the dashboard read.

06

Model routing applies

Roles — worker, triage, verifier, research, plan — can each be pinned to a different model. Every route that uses a role honors the pin.

Why this matters for a new hire. If you find a bug in the step loop, you have found it on all six routes at once. That is the point of the design — and it is also why the engine crate is not allowed to touch a file, a socket, or a provider SDK directly.

Part 2 · 05

You press Enter

Nothing has reached a model yet. Six things happen first, and they happen in this order every time.

Before the first model call
  1. The text is captured. In the Command Deck it may also be queued behind a turn that is still running — prompts do not interrupt, they line up.
  2. Session hooks fire once. SessionStart runs when the session opens, not per turn. The engine deliberately never fires it: the host owns it, because the host is the one assembling the prompt.
  3. The stable prompt prefix is assembled — base instructions, environment facts, workspace memories, published rules. Same bytes every turn.
  4. Recall runs — relevant memories and skills for this prompt, gathered fresh, added as a separate volatile block afterward.
  5. A budget guard is built from the spend limit, and a record is opened in the store.
  6. A route is chosen — raw turn or staged pipeline — and the first step begins.

Common new-hire mistake. Assuming the system prompt is built once per session. It is built per turn — but built to be byte-identical per turn. Those are different things, and the next two slides are about why the difference matters.

Part 2 · 07

Why the order of those layers matters

Model providers cache the front of your prompt. They match it byte for byte, from the very first character. The moment one byte differs, the cache stops matching from that point on — and you pay full price for everything after it.

Interactive · what one changed byte costs click either arrangement

The three rules that fall out of this

Memories load once, sorted

Workspace memory files are read once per session and joined in sorted filename order. Sorted, so the bytes cannot depend on how the filesystem felt that day.

No clock in the prefix

Today's date is genuinely useful — and genuinely changes. So it rides the volatile recall block, never the stable prefix.

Dropped items are named

If pinned rules overflow the prefix budget, the ones dropped are listed by name — and the list is computed the same way every time, so even the overflow message is stable.

Say this out loud once. "Prompt caching is a feature, so anything that makes the prefix wobble is a cost regression, not a style issue." That sentence is an architectural invariant in this repository, not a preference.

Part 2 · 08

Recall: what this prompt needs

Two different things get pulled in, from two different places, and they behave differently.

MEMORIES

Things the agent learned before

Stored in a local database with tags for the parts of the codebase they touch. The prompt is used to find the relevant ones — not all of them.

SKILLS

Reusable how-to notes

Markdown files under .stella/skills/. A selector picks the ones matching this prompt and pastes their text in. Skills are never forced — they are offered.

prompt  ──▸ recall (memories) + select_skills (skills)
          └─▸ one volatile message, placed AFTER the stable prefix
              …turn runs…
outcome ──▸ reflection ──▸ 0–3 lessons ──▸ memories + the mining log
                                      └─▸ enough repeats ──▸ a new skill file

Best-effort by contract. If the memory store is broken, recall returns nothing and the turn runs anyway. A failure here must never fail or slow down the actual work. "Degraded" means "no memory this turn" — it never means an error the user sees.

Part 3 · 10

The safe boundary rule

Everything that ends a turn ends it between steps. Never in the middle of a tool.

Budget aborts, the pause button, the soft stop, loop-detection aborts — all of them wait for the current step to finish. Killing a tool halfway leaves the files in one state and the model's picture of them in another, and the model then reasons from a picture that is wrong.

Where a turn may and may not stop

The design trick that enforces it

The budget code is structurally unable to stop anything. It returns a recommendation — "you should abort" — and a separate function between steps is the only thing that can turn that into a stopped turn. You cannot accidentally add a mid-tool abort, because the piece that notices the problem has no power to act on it.

The one exception, and it is not an exception. A tool that runs too long (15 minutes by default) is cut off — but the result is an error handed back to the model as a tool result, not a stopped turn. The model sees "that timed out" and routes around it. The turn keeps going.

Part 3 · 11

Compaction: making it fit

Conversations grow. Model context windows do not. Before every model call, Stella measures the conversation and — if it is too big — shrinks it using four mechanisms, applied least damaging first.

Interactive · compaction simulator drag the budget down and watch which mechanism fires

The four mechanisms

OrderMechanismWhat it doesWhich copy it keeps
1DedupTwo tool results with byte-identical text — stub out the copies.the earliest
2SupersessionThe same call run again — the old result is stale.the latest
3AgingOld, large outputs get their middles cut out.head + tail
4EvictionDrop old tool results entirely. The blunt one.never the newest

The thing that looks like a bug and is not. Dedup keeps the earliest copy; supersession keeps the latest. Same-looking rule, opposite direction. Dedup is about identical content — position does not matter, so keep the earliest and the cached prefix stays byte-identical. Supersession is about staleness — the whole point is that the new one is right and the old one is wrong. Two tests pin both directions so nobody "fixes" one into the other.

The system message and the newest user message are never touched by any of the four.

Part 3 · 12

Loop detection: noticing it is stuck

Models get stuck. They run the same command, get the same answer, and try it again. Loop detection watches the recent history for exact repeats and short cycles, and can end the turn rather than burn the budget on it.

Interactive · is this a loop?click a case

Two subtleties worth memorizing

The call id is ignored

Providers mint a fresh id for every call. If the detector compared ids, no two calls would ever look alike and it would never fire. So it compares name, input, and output — and ignores the id. This is the one place in the codebase that distinction is made.

A repeat is only a loop if the output repeats too

Same command, changing output is legitimate work — polling a build, re-running a test suite that is shrinking. Only same-in/same-out counts.

Why phase order matters here. Compaction rewrites tool results in place, and loop detection runs on the rewritten history in that same step. So Stella takes a snapshot of what each result really was before compaction, and detection compares against the snapshot. Without that, compaction could make two different results look identical and trigger a false loop abort.

Part 3 · 13

The model call, retries, and running ahead

One logical call, many attempts

The model call is wrapped in a retry ladder with backoff. From the outside it is one call — the "started" and "completed" events bracket the whole ladder, not each attempt. Retries show up as their own separate events, so nothing is hidden, but an observer counting requests counts one.

The exactly-once guarantee, and its exact limit. A tool that changes things runs outside the retried block, after a model call has already succeeded. So a retried step structurally cannot re-run an edit. Read-only calls carry no such promise — they run inside the retried block. If a "read-only" tool has a side channel (a rate-limited API, a write to an index) it can genuinely run more than once in a step.

Speculation: starting early

Model responses stream in. If the first thing announced is a read-only call, Stella can start running it while the rest of the response is still arriving — hiding that work behind generation.

Interactive · how far speculation gets click a call to flip it between read and write

Fenced by the first write

Calls stream in order. The instant a call appears that is not read-only, speculation stops for the rest of the step. Only the all-read prefix ever runs early.

Harvested only on an exact match

A speculative result is used only if the committed call matches byte for byte — same id, same name, same input. Anything else is thrown away and reported, so the work it already did stays visible instead of vanishing.

Part 3 · 14

Tool dispatch: running what was asked for

The model may ask for several tools at once. Running them all in parallel would be fast and wrong. Running them all one at a time would be correct and slow. Stella does neither — it groups them.

The rule: consecutive read-only calls form one group and run together. Anything that can change something runs alone, as its own barrier, in the order the model asked.

Interactive · the scheduler click a call to flip read ⇄ write and watch the grouping change

Why it is safe

Anything watching changeable state cannot tell this schedule apart from running everything one at a time. A read placed after a write is guaranteed to see that write, because the write was its own barrier and finished first.

Why it is fast

The common step is "read five files" or "answer three research questions". Those get real parallelism. Results come back in whatever order they finish — but the list handed back to the model is always in the original order, so the conversation stays identical every run.

Part 3 · 15

Who is allowed to say no

Between "the model asked for a tool" and "the tool runs" sit several things that can refuse. They all speak the same four-word vocabulary, and they fold together in one fixed order.

The decision ladder
VerbMeaningEffect on the chain
allowFine by me.Keep going down the chain.
modifyFine, but change the input first.Folds in, chain continues.
require_approvalAsk a human.Short-circuits, parks for an answer.
denyNo.Short-circuits immediately.

The failure posture is the important part. A checker that crashes, never runs, or prints something malformed has not made a decision. That counts as an unconditional deny — and no "make enforcement lenient" flag can soften it. A broken guard must never read as an open door.

Plain prose printed by a hook is treated as information, not a decision — the old contract (exit zero allows, non-zero blocks) still holds for hooks that never print one.

Part 3 · 16

Every way a turn can end

There are exactly these. Anything else is a bug.

NORMAL

The model stopped asking

It returned an answer with no tool calls. This is the good ending, and by far the most common one.

LIMIT

Max steps reached

A backstop so a confused turn cannot run forever.

MONEY

Budget aborted

The spend cap was hit. Checked between steps, twice per step — before and after compaction, because compaction itself can cost money.

STUCK

Loop detected

Same call, same output, over and over. Ends rather than burning the budget on it.

HUMAN

Soft stop (Esc)

A choice, not a failure. Stops at the next boundary and keeps every completed step. No error is emitted.

HUMAN

Hard cancel (Esc Esc)

Stops now. The whole turn is dropped from history by the caller — because stopping mid-dispatch can leave a half-finished pair of messages the next call would reject.

The distinction that will bite you. A soft stop keeps the transcript, so the engine carefully closes any open tool call with a placeholder result to leave the history valid for the next turn. A hard cancel discards the transcript, so it does not bother — and a caller that keeps a hard-cancelled turn's messages anyway has to close that pairing itself. That is a contract, written down, not an accident.

Part 3 · 17

When things go wrong mid-turn

Four recovery paths run inside the loop without the user ever seeing a failure. Each one exists because a real run died of it.

TOO BIG

Context overflow

The provider says "your prompt is too long". Instead of giving up, Stella recognizes that specific rejection, tightens the compaction budget, and re-runs the same step. Providers phrase this differently — which is exactly why each one has to declare on paper whether its phrasing is recognized.

TOO MUCH

Output ceiling refused

Some gateways price a request against the ceiling you asked for, not what you spend — so a big ceiling gets refused even when the balance is plenty. Stella lowers the ceiling and asks again. Unrecognized, this killed three benchmark runs outright.

FLAKY

Broken stream

A stream that hangs before its first byte, or a success code with nothing in it. The retry re-issues the attempt as a plain non-streaming request.

WAITING

A parked wait

A tool can ask the turn to pause until something changes — a file, a deadline. The engine polls on its own clock through the tools it already has, spending zero model calls, and wakes the model to the difference.

The pattern to notice. Every one of these turns a hard failure into a tool result or a retry the model can reason about. The engine's instinct is never "abort and tell the human" while a recoverable path exists — but a recovery that cannot be trusted always fails loudly instead of quietly guessing.

Part 4 · 18

Route A — the raw turn

The shortest path. No planning, no proof — the model works until it decides it is done. You are the verification.

Doors: stella run --no-pipeline "…" · stella --plain · Command Deck with /pipeline off.

End to end · raw turn

Best for

Questions, small mechanical edits, anything you were going to look at yourself anyway.

Costs

Cheapest and fastest. One model call per step and nothing else.

Gives up

Any structural claim that the work is correct. Nothing checked it but you.

One tool is withheld on the one-shot door. The session task board. A one-shot turn has nothing to resume, so a task card costs a model round trip and buys legibility nobody is watching for. Delegation to sub-agents is not withheld — that spends money to do actual work, which is a different trade.

Part 4 · 19

Route B — the staged pipeline

The default for stella run and for Command Deck turns. It wraps the same step loop with planning before and proof after.

End to end · staged pipeline the gold box is the whole of Part 3

Two rules that shape the whole thing

Verification buys no model call

The verdict is not a model's opinion. It comes from measurements — did a command flip from failing to passing, what does the diff say. There is exactly one extra model call in the whole verification story, and it is the one that writes the test. That survives because it creates the measuring stick rather than replacing it.

The engine owns its turn's ending

Each turn ends with the engine's own event, meaning this turn is over — never the work is over. A plan step or a revise round just asks for another turn, and three turns put three endings in the journal, unedited. The pipeline's own ending is a separate event with a separate name, emitted once and last.

crates/stella-pipeline/src/pipeline.rs — "Event ownership"

This one changed, and it is worth knowing why. The pipeline used to hand every turn a private channel and forward everything except the engine's own ending, so it could be the single authority on when a run was over. That was a two-way connection between the engine and one of its callers — and a dropped event or a double-closed channel produced a run that looked finished and was not. It is now one-directional (#3379): the wrapper reads the engine's stream, it never edits it.

Part 4 · 21

The witness — proof, not opinion

Stella's definition of "done" is a test that fails before the change and passes after. Not a model saying it looks right.

The flip

Four rules that make the proof mean something

01

A different model writes the test

Never the model that did the work. Someone marking their own homework proves nothing.

02

The author is blind to the change

It works in a clean copy of the tree from before the work. It cannot see the diff — so it cannot write a test that just restates the patch.

03

Three tools, and no more

Read a file, list files by pattern, create exactly one test. No shell, no writes, no network. Enforced by its executor, not by asking nicely in a prompt.

04

Tampering voids the credit

The test file's identity is pinned. A worker that edits the witness does not get credit for "passing" it.

Honest failure is a feature. If a witness cannot be produced — no test runner answered, the author declined — the run degrades to "unverified", with the reason stated. If a witness cannot be trusted — tampering, wrong file, identity mismatch — the candidate is stopped. Those are deliberately different outcomes.

Part 4 · 22

Route C — a turn inside a turn

A sub-agent is a child turn whose transcript is thrown away. Only a short summary comes back.

The point is not speed — fleet mode already does parallelism. The point is context economy. Work the parent would otherwise carry, and re-send on every future step for the rest of the session, is absorbed by a conversation that simply goes out of scope.

Interactive · what the parent keeps toggle delegation on and off

Four rules

RuleWhy
The budget is carved, not grantedThe child gets the smaller of what it asked for and what the parent has left, so a spend limit stays a hard ceiling once turns nest.
Spend settles back exactly once, on every pathIncluding failure — a child that aborted still spent what it spent.
Failure is a value, never an errorA failed child returns a typed outcome. It cannot kill the parent turn. An aborted child even salvages its last answer.
Steering is filtered, not inheritedDraining steering is destructive. A child that inherited it would swallow a message the user aimed at the parent. So the child forwards the stop signal and returns nothing for the drain.

A real bug worth knowing. The public constructor cannot carry the gate, steering, and hooks — those are private builder fields. So a hand-rolled child engine silently drops all three. Goal mode shipped with exactly that bug. Never hand-roll a child; call the sub-agent function, which builds it inside the crate with every seam attached.

Part 4 · 23

Route D — goal mode

Goal mode flips the contract: you say what must be true when it is done, not what to do. Then it works in rounds until that is true.

End to end · goal rounds

The verifier is independent

Routed to a different model family from the worker whenever possible, and it judges from evidence — running tests, reading CI, inspecting files — never from the worker's claims about itself.

The verifier physically cannot cheat

It holds a read-only view of the same tool stack. Only tools marked read-only are even visible to it. It structurally cannot edit its way to a passing verdict.

Each working round is a pipeline run by default; --no-pipeline makes rounds raw turns instead. Two layers of verification is real rigor and you pay for it in money and time — drop the inner one when the goal verifier alone is enough.

stella monitor is not a seventh route. It is goal mode with the goal pinned to "the latest CI run for this target is fully green". Same machinery, fixed objective. Only a green board ends the loop.

Ending honestly. If a round cap, a spend limit, or a worker abort ends the run first, it ends as not met. It never rounds up to success.

Part 4 · 24

Route E — fleet workers

For when the work is many tasks, not one. A dependency-ordered task graph fans out to parallel workers.

End to end · fleet

Same engine per task

Each worker drives the pipeline when available, the raw loop otherwise. Nothing new below the waterline.

Two isolation modes

One shared tree with cooperative file claims, or a dedicated private worktree for tasks marked isolated.

Its own ledger

Every run, task, attempt, commit, and dollar lands in a separate fleet database for later review.

One budget difference from sub-agents. A deck sub-agent's spend lands in the session's shared guard. Fleet children each run under their own slice of the cap. Same word — "child" — different money model.

Fleet mode gets its own deck. What matters here is that it does not introduce a third loop.

Part 4 · 25

Route F — serve, one step at a time

The only door that drives run_step itself instead of letting run_turn loop. That single difference is what makes it durable.

Who drives the loop

The host holds the crank

It calls one step, gets a state back, can save that state to disk, and can pick up later — even in a different process. The engine holds no conversation state of its own, which is what makes this possible at all.

The engine holds no authority

Every model call and every tool call is handed back out to the host to perform. The engine decides; the host acts. It is its own binary and nothing in the CLI links it.

Careful with "resume". The CLI does not resume at step granularity — it resumes at transcript granularity, reopening the conversation at the checkpoint's step boundary. Serve stores a step state and hands it back on request but accepts none in return. Both of those are declared positions, written down in a parity table, not oversights.

Part 5 · 27

Writing the turn down

When the turn settles, several things get recorded — in different places, for different readers.

STORE

The execution record

Files touched, tools used, memories cited, cost, outcome, which door. Lives in the workspace's local database. Feeds stats and the dashboard.

EVENTS

The event journal

A line per thing that happened. This is ground truth — the summaries and dashboards are all just projections of it. When a run's behavior is in question, this is the file to open, never the summary.

RECEIPTS

Context receipts

What went into each model call, recorded as fingerprints — never the actual text. Enough to audit, not enough to leak.

HUB

The cross-project hub

Per-call rows copied up to a user-wide database so you can ask "what did I spend across every project this month".

Zero telemetry leaves the machine by default. Not "anonymized", not "aggregated" — zero. The only network traffic is to the model provider you chose. This is enforced by a reviewed allow-list plus a test harness, so adding a column that could carry content fails the build until a human answers "is this content?".

Part 5 · 28

Reflection → memories → skills

After a turn that did real work — success or failure — the agent looks back at what it just did and writes down what it learned.

Interactive · the learning path click a stage

One cheap call

Reflection runs on the cheap tier, not the worker's model. It produces at most a few lessons — never an essay.

Failure is the best signal

A failed turn gets a different, root-cause prompt: "why did this fail?" That is the highest-value learning a session produces.

Repetition promotes

Lessons land in a log. When the same lesson recurs enough times, it is promoted automatically into a durable skill file.

And then the loop closes. That skill file is exactly what the recall step at the start of the next turn can select and paste in. Slide 08 and this slide are the two ends of the same circle.

The full story — skill mining, promotion tiers, self-tuning — is deck two, Stella Self-Improvement.

Part 5 · 29

The tool foundry (short version)

If the agent keeps typing the same shape of shell command by hand, it should be offered a real tool for it instead.

Interactive · from commands to a proposal click a history to see whether it earns a tool

How it works, in three sentences

  1. Each command is reduced to a signature: the parts that stay (program name, subcommands, flag names) kept as-is, the parts that vary (quoted text, paths, numbers) replaced by typed holes.
  2. Two commands with the same signature are the same shape — and the holes become the proposed tool's parameters.
  3. A shape must show enough variation to not be an exact repeat, and enough reuse to not be a shell wearing a costume, before anything is proposed.

Why the upper bound exists. Pointed at a real 81,684-command history with only a lower bound in place, it produced 2,073 proposals — an inbox nobody would ever read. A shape used 1,954 times with 1,938 different argument sets is not a tool. That is sed, and minting a "tool" for it would be wrapping the shell in the shell.

Contrast with loop detection. Loop detection looks for a turn that is stuck — same call, same output, again and again. The foundry looks for the opposite: the same shape reused with variation. They are deliberately complementary, which is why an exact repeat is explicitly not a foundry proposal.

Part 5 · 30

Where the loop is going — wrappers become plugins

Everything in Part 4 describes what ships today: one step loop, one built-in wrapper, and the wrapper is still the default. The direction is to keep the loop and move the wrapper out of the binary. Some of that has landed. Most has not, and this slide says which is which — because a deck that promises the end state is how a reader ends up believing a shipped binary already has it.

The four points a wrapper gets

PointWhen it runsWhat it may doWhat it may not do
before_turnbefore the loop is asked for a turn add context, pick a plan, narrow scope, choose a model rolerun the loop itself
after_turnonce the turn's ending lands gather evidence — run a test, read a diff, author a witnesschange the turn that just ran
judgeafter after_turn turn the evidence into a verdictcall a model
again?after judge ask for another turn, or stop with an outcomefake an ending the engine did not emit

judge and again? are synchronous and the host runs them, so a plugin declares its verdict rule as data and supplies evidence — it never ships verdict code. That is the same rule the staged pipeline already keeps, carried across rather than re-argued.

LANDED

The parts you can read today

The engine owns its turn's ending, so no wrapper holds a private channel (#3379). The wrapper socket exists — four points, two transports, and the wire one is what CI exercises (crates/stella-runtime/src/wrapper/). A manifest grammar and an installer exist (stella plugin). Turn records already separate which door from which wrapper ran, and a NULL there means the raw loop, which is a fact rather than a missing value.

NOT YET

The parts that are still ahead

Nothing dispatches through the socket: every call to it in the tree is in its own tests (#3494), and no installed plugin's hooks are routed into a session either (#3521). The staged pipeline is still a built-in crate, still the default, and --no-pipeline is still the opt-out. Inverting that flag is deliberately the last move, because it is the claim that the earlier ones worked.

How to read this deck against the binary. Slide 03 says two loops, six doors, and that is still literally true of what you install. The end state is one loop, six doors, and zero built-in wrappers — at which point slide 03 gets rewritten, not before.

If you remember five things from this deck

  1. There is one step loop and one optional wrapper. Six doors, two loops.
  2. Twelve phases per step. Six ask "should we call the model", one calls it, five handle the answer.
  3. Turns end at step boundaries, never mid-tool. The budget cannot abort anything by itself — that is deliberate.
  4. Reads run in parallel; anything that writes runs alone, in order.
  5. Done means a test flipped, not a model said so.

Appendix · A2

One-page cheat sheet

The twelve phases, in order

  1. Cancel check
  2. Pause gate
  3. Steering drain
  4. Soft-stop check
  5. Budget check
  6. Snapshot result identities
  7. Compaction pass
  8. Loop detection (+ 2nd budget check)
  9. Model call, with retries
  10. Committed-result bookkeeping
  11. Tool dispatch
  12. Parked wait, then step++

The order rules that are bug fixes

  • Snapshot before compaction — compaction rewrites results in place.
  • Steering drains before compaction — so the pass sees the new message.
  • Steering drains before the soft-stop check — a note typed just before Esc survives.
  • Cancel check before the pause gate — a paused-and-cancelled turn must not park forever.

Parallel or not?

  • Read-only, consecutive → parallel group.
  • Anything that writes → alone, in order.
  • Results always returned in original order.

Money

  • Checked twice per step, always between steps.
  • Budget code cannot abort — it recommends.
  • Child budgets are carved from the parent's remainder.
  • Child spend settles back exactly once, even on failure.

The sentence to carry around. "One model call per step, twelve phases around it, and nothing ends a turn except at a step boundary." Everything else is detail you can look up.
